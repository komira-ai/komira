# Generated sources are committed and checked for freshness

Status: decided. The mechanism is built and applies to the libraries that have a committed `generated/<name>/`; the rest are
listed in [transition.bzl](../../tools/build/gen/transition.bzl) and still build from the generator (see "The transition
ledger"). The line-limit split is a separate change (see "The line limit").
Reference for the mechanism: [tools/build/gen/README.md](../../tools/build/gen/README.md).

## What problem does this solve?

Some libraries are not written by hand. `mojo_aws_client`, `mojo_gcp_client`, `mojo_proto_library` and
`mojo_db_proto_library` run a generator (`aws-client-gen`, `protoc-gen-mojo` and its siblings, from
[tools/build/proto-codegen](../../tools/build/proto-codegen)) over a pinned input (a service model or `.proto`
files) and compile the output. Before this decision the output existed only inside a build action. Then:

- A reviewer of a change that moved a model pin or the generator saw no change in the code that ships.
- The sources of the package set were not all files in the tree. A tool that reads a package's committed sources
  (the package manager's unit graph hashes the `.mojo` files of a library directory, offline and without running a
  program) could not see them.
- Nothing proved that the sources a library was built from were the ones the generator writes today, except
  running the generator.

The requirement: generated sources are part of the package set's reviewed, reproducible sources, and a stale one
cannot produce a library.

## Which options were weighed?

| | A: commit the output, plus a freshness gate | B: a generated-source input in the package graph | C: generate at stage time only |
|---|---|---|---|
| What a library is built from | the committed files | files the graph lists as generated, each with the generator's pin and the output's sha256, verified at build | the generator's output, produced when the set is staged |
| Fits the unit graph as specified | yes: sources are committed files, hashed offline | no: needs a new source kind, a manifest section for the generator and a lock entry | no: a source that is not a committed file is invisible to the graph |
| Review | the output is in the diff | the diff is the changed hash | none: the sources are never seen |
| Proof of freshness | the gate fails when the generator's output differs from the commit | the build recomputes the hash | none beyond the build being reproducible |
| Cost | repository size; a generator change comes with a large regeneration diff | a change of the graph format and of every consumer of it; the graph's rule of running no program has to move into the build | the lock of a dependent cannot name a hash that exists only after staging |

**Choice: A.** It is the only option that works with the sources the package tooling reads today, it needs no
change of any format, and it keeps what the build already promises: a welded test cannot pass on a stale file,
because the freshness check fails first. B is the better shape if committed bytes or regeneration diffs become the
cost (see "When would B be reconsidered?"). C is rejected: it leaves the generated libraries outside the proof of
the set, and its lock cannot name an output before the output exists.

A package installed from a registry holds a compiled `.mojoc`, not sources, so the choice changes nothing for an
installer under any option. It decides how the build side proves what was compiled.

## The single-path rule

For a library that has been migrated (not listed in the ledger), `<name>` is built from `generated/<name>/` of its package and from nothing else.
`<name>_gen` (the generator's output for the current inputs) is read by `<name>_fresh` only. `<name>_fresh`
regenerates, compares file by file and byte by byte, and on a difference fails with the command that rewrites the
directory:

```text
./buck2 run komira//tools/build/gen:regen -- <library target>
```

`<name>_fresh` is the library's first gate, a hidden input of its compile, so no `.mojoc` exists and no test of
the library is built while the commit is not what the generator writes. A migrated library has no second path that
compiles from `<name>_gen`: a parallel way would rot. The one exception is the transition ledger below, which has an
end: a listed library still builds from the generator until its commit lands.

Both halves are deterministic, and that is tested: every emitter writes its header through one function, the
output has no host path, time or user, and files are written sorted with one mode.

## What does a generated file look like?

The first line is `# @generated by <generator> version <n>`. The lines after it pin each input by name and sha256,
and the last says not to edit the file and gives the regeneration command
([header.rs](../../tools/build/proto-codegen/src/header.rs)). A tool that must tell a generated file from a written
one matches the token on line 1 and nowhere else.

## How big is it?

What is committed today: four libraries have a `generated/<name>/` directory (one AWS client, one Google Cloud client
and two proto libraries); every other generated library is in the ledger.

The figures below are a projection for the full migration, not what is committed. They were measured on the farm, at
the time of writing, from the generator outputs of every generated library: about 10 MiB and about 207,000 lines
across 48 generated targets. That is the size the repository reaches when the ledger is empty.

This is the cost of A, and it is accepted because it is paid in repository size and in regeneration diffs, not in
build time: an unchanged library's check is a cached action.

## The line limit

Source files stay under 1000 lines (Mojo hangs on very large files). A generated module that would be larger is
split by the generator into a facade module and a `_parts/` directory, so that every committed generated file is
under the limit. `regen` and `_fresh` carry subdirectories like any file, so `_parts/` is compared and committed
the same way. The split is a change to the generator, not to the rules. Until it lands, a generated module can
exceed the limit.

## Coverage

Generated files are not measured. A `.mojo` file whose line 1 starts with `# @generated` is set aside by the
coverage gate: it is neither measured nor counted as an unmeasured file, and is in no floor. The exclusion is
visible in the gate's summary, in its result JSON (`generated_paths`) and in each package's committed
`coverage_census.tsv`, so a hand-written file that gains the header shows up as a diff. See "Generated sources" in
[the coverage README](../../tools/build/coverage/README.md) and [census.md](../../tools/build/coverage/census.md).
The tests of a generated library are written by hand and measure the hand-written code around it; the generated
code is held by the layout probe (its first test) and by the generator's own tests.

## The transition ledger

Libraries that predate this decision are listed in [transition.bzl](../../tools/build/gen/transition.bzl). A listed
library has no `<name>_fresh` and no committed directory, and is built from the generator as before. The list only
shrinks: migrating a library is one commit that deletes its line, lowers the count the lint holds, runs `regen` and
commits the directory. A line for a library that has a committed directory is an error at load, a new generated
library starts committed and is never listed, and when the list is empty the code that builds from `<name>_gen` is
deleted. A repository that uses komira as a cell lists its own libraries in `.buckconfig`
(`[komira] generated_unmigrated`).

## Third-party text

The committed files are derived from third-party inputs: the AWS service models of botocore for the AWS clients,
and googleapis `.proto` files for the Google Cloud clients. Both are Apache-2.0, and neither input is committed:
the archives are pinned by sha256 and fetched at build time
([third_party/botocore/BUCK](../../third_party/botocore/BUCK),
[tools/vendor/googleapis/BUCK](../../tools/vendor/googleapis/BUCK)). Only the derived text is. The root
[NOTICE](../../NOTICE) records the attribution.

## When would B be reconsidered?

B is the follow-up if either cost of A turns out to be real:

- regeneration diffs are routinely over about two thousand lines, so that review of a generator change is
  skimming;
- the committed size makes clones or the CI checkout a cost that matters. The measurement above is already twice
  the first figure considered (about 5 MiB); A was kept because the size costs storage and not build time, and
  this is the number to re-measure;
- the package tooling gains a source kind for generated output on its own account.

B changes the unit graph format and every consumer of it, so it needs its own design first. Nothing in A blocks it:
the generator, its header and its pins are what B would hash.

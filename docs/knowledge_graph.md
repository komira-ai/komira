# The knowledge graph

komira keeps a small, committed knowledge graph of itself, so that a person or an agent can
answer "what is this library", "what depends on this target", "which tests cover this file"
and "which doc is the authority for this" with a file read or one command, without building
anything. It is generated by [`tools/kg`](../tools/kg/README.md) and configured by
[`docs/kg.toml`](kg.toml).

## What is committed

| File | What it holds | Rebuilt by |
|---|---|---|
| `docs/libraries/<id>.md`, `docs/libraries/README.md` | One page per `mojo_library` (label, summary, welded tests, entry points, governing docs) and a one-line-per-library map | the pre-commit hook |
| [`docs/kg/docs_graph.json`](kg/docs_graph.json) | Every Markdown doc under `docs/` and at the top level: its title, the repository paths it references, the libraries it `governs:`, and what it is canonical for | the pre-commit hook |
| [`docs/kg/buck_graph.json`](kg/buck_graph.json) | Every target in `//...`, `checks//...`, `mojo//...` and `toolchains//...`: its rule kind, deps, `srcs` and welded `test_srcs`, plus a fingerprint of the inputs it was rendered from | `python3 tools/kg/kg.py graph` (buck2) |

All three are sorted JSON or Markdown with no timestamps, counts or line numbers, so a
change to the tree changes only the lines it should. The canonical-doc table is
[`docs/index.md`](index.md); there are no rulings yet.

Query the Buck2 graph without buck2:

```sh
python3 tools/kg/kg.py rdeps komira//examples:hellopkg   # what depends on it
python3 tools/kg/kg.py tests examples/hellopkg/greet.mojo  # what tests cover a file
python3 tools/kg/kg.py owner examples/hello.mojo          # which target lists a file
```

## Enable the hooks (once per clone)

```sh
python3 tools/kg/kg.py setup    # sets core.hooksPath=.githooks, then self-checks
```

The hooks need git 2.25 or newer and Python 3.9 or newer, and nothing else: **no hook runs
buck2.** `setup` refuses to replace a `core.hooksPath` you already set.

## Who checks what

| Step | Runs buck2? | What it does | What it refuses |
|---|---|---|---|
| pre-commit (`.githooks/pre-commit`) | no | Rebuilds the pages and the docs graph from the commit's index and stages them; compares the Buck2 graph's recorded fingerprint with the index | a dead doc reference; a generator change the commit does not hold. A Buck2 graph from other inputs is only a WARNING here |
| pre-push (`.githooks/pre-push`) | no | `kg check` of each new branch tip, with that tip's own generator | stale pages or docs graph, a dead reference, a Buck2 graph from other inputs |
| `kg` workflow, every pull request | yes, loading only | `kg check --graph`: the pre-push check, plus one `buck2 uquery` whose output must equal the committed graph byte for byte; then the kg test suites | all of the above, and a graph whose inputs match but whose bytes do not |
| `kg` workflow, push to `main` | yes, loading only | the same check, then uploads the three generated files as a workflow artifact | the same |

The Buck2 half is a split on purpose. The query is loading only (`uquery`: no configuration,
no actions, no remote execution), but it starts a buck2 daemon, and a hook that needs a
daemon or a download is a hook people disable. So the hook checks a fingerprint (the build
files, every `.bzl`, `.buckconfig`, the buck2 pin, and the paths of the files inside
packages), and CI proves the bytes.

`kg graph` and `kg check --graph` never query the working tree. They check the tree being
graphed (the index, or the commit) out into a scratch directory and run buck2 there, with a
daemon of its own that is stopped afterwards. So a `.buckconfig.local`, an untracked or
ignored file, or an unstaged edit cannot change the bytes, and a contributor renders exactly
what a clean CI checkout renders. `[graph] config` in `docs/kg.toml` passes placeholder
`-c komira_re.*` values so that clean tree loads every package; the placeholders appear
nowhere in the output.

Every cell in `.buckconfig` `[cells]` is either queried whole (`<cell>//...` in `[graph]
universe`) or named in `[graph] exclude`. A cell in neither makes the graph stale and
`kg graph` refuses, so a new cell cannot go unindexed while the check reads fresh.

**When a check is red**, it names the fix:

```sh
python3 tools/kg/kg.py build --all && git commit -m "kg: refresh pages" -- docs/libraries docs/kg
python3 tools/kg/kg.py graph && git commit -m "kg: refresh the Buck2 graph" -- docs/kg
```

## Settings that are not files

- Branch protection on `main` should require the `kg` check and "require branches to be up
  to date before merging" (or a merge queue that runs it): GitHub does not re-run a pull
  request's checks when `main` moves.
- CI does not commit. A bot that commits the regenerated files on push to `main` would need
  a write token in the workflow and would race human pushes; it is a decision for later, and
  until then a red check names the one command that fixes it.

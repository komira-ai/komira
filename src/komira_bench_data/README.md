# komira_bench_data

The datasets of the komira benchmarks. A benchmark is only worth publishing if anyone can tell which bytes it ran on, so this package pins a dataset down to files, sizes and checksums, checks a directory of files against that, writes a lock that names the exact dataset a run used, and generates the h2o-style tables from a seed.

Nothing here ships data. A package is a compiled library, so no dataset is in it, none is committed to a repository, and this package downloads nothing. Datasets live in a cache directory that the caller names (an argument; no environment variable is read). TPC-H is generated by the pinned DuckDB through `komira-bench-stage` (below); ClickBench is supplied.

## Modules

| module | holds |
| --- | --- |
| `manifest` | `DatasetManifest` and `DatasetFile`: a dataset at a scale and its files, each with an expected size, sha256 and row count; the manifest of every supported dataset (`tpch_manifest`, `clickbench_manifest`, `h2o_groupby_manifest`, `h2o_join_manifest`, `supported_manifests`, `find_manifest`) |
| `verify` | `verify_dataset` checks a cache directory against a manifest and returns a `VerifyReport` of `FileCheck`s; `sha256_of_file` streams a file in 4 MiB chunks |
| `lock` | `DatasetLock`, `lock_from_report`, `encode_lock`, `decode_lock`, `lock_file_path`, `write_lock_file`, `read_lock_file`, `verify_against_lock` |
| `draw` | the generators' number source: `draw`, `draw_range`, `draw_score` and `Bijection`, pure functions of seed, column and row |
| `h2o_groupby`, `h2o_join` | the tables as Arrow batches for any row range (`h2o_groupby_batch`, `h2o_join_batch`) |
| `h2o_files` | the tables as Parquet bytes and as files (`h2o_groupby_parquet`, `h2o_join_parquet`, `generate_h2o_groupby_files`, `generate_h2o_join_files`, `write_new_file`) |
| `stage`, `stage_extension`, `stage_cli` | staging TPC-H through the pinned DuckDB (`generate_tpch`, `render_stage`), the pinned tpch extension (`tpch_extension_pins`, `prepare_extension`) and the `komira-bench-stage` command (`run_stage`) |

## What a manifest records

Each file of a dataset has a path relative to the cache directory and three expectations: its size in bytes, its sha256 and its row count. Any of them can be unrecorded (`UNRECORDED_BYTES`, `UNRECORDED_ROWS`, an empty sha256). A value is filled in only where it is known for certain; every other value is recorded from the first verified run, and the verifier reports what it observed so that there is something to record.

| dataset and scale | files | recorded today |
| --- | --- | --- |
| `tpch` `sf1`, `sf10`, `sf100` | `tpch/sf<N>/<table>.parquet`, eight tables | row counts from the specification's cardinalities (lineitem at sf1 only); sizes and checksums once staged and recorded |
| `clickbench` `full` | `clickbench/hits.parquet` | size and row count |
| `h2o_groupby` `n<rows>_k<groups>_seed<seed>` | `h2o/groupby_<scale>.parquet` | row count |
| `h2o_join` `n<rows>_seed<seed>` | `h2o/join_<scale>_{x,small,medium,big}.parquet` | row counts |

`recorded_files()` holds the recorded sizes, checksums and row counts, and `tpch_manifest` and `clickbench_manifest` apply it (`apply_recorded`). Nothing is recorded yet, so a first verification reports every file as `UNRECORDED` with the size and sha256 it observed.

```mojo
from std.testing import assert_equal, assert_false
from komira_bench_data import find_manifest

var tpch = find_manifest("tpch", "sf1")
assert_equal(len(tpch.files), 8)
assert_equal(tpch.files[7].path, "tpch/sf1/lineitem.parquet")
assert_equal(tpch.files[7].expected_rows, 6_001_215)
assert_false(tpch.files[7].has_sha256())

var hits = find_manifest("clickbench", "full")
assert_equal(hits.files[0].expected_bytes, 14_779_976_446)
assert_equal(hits.files[0].expected_rows, 99_997_497)
```

## Staging the data

The decision, in five lines: TPC-H comes from the pinned DuckDB CLI (1.5.6, the same binary and release as the comparison arm) running the `tpch` extension's `CALL dbgen(sf=N)` and `COPY (SELECT * FROM <table>) TO ... (FORMAT PARQUET, COMPRESSION snappy, ROW_GROUP_SIZE 122880)`; the extension is the gzip the caller passes as DuckDB's extension repository serves it, and it is pinned by size and sha256 per DuckDB release and platform in `tpch_extension_pins()` (one pin today, linux_amd64 for 1.5.6, measured by a reviewer's download because DuckDB publishes no checksum, so trust on first use as of that measurement); anything else is refused before DuckDB is started, the pinned bytes are unpacked into a private directory and DuckDB loads that copy (auto-install and auto-load off); files live where the manifest says, `<cache>/tpch/sf<N>/<table>.parquet` and `<cache>/clickbench/hits.parquet`; ClickBench's `hits.parquet` (14,779,976,446 bytes, 99,997,497 rows) is the public single file, fetched by the benchmark host's runbook, never by this package, and verified by size now and by sha256 once recorded; the first checksums are measured by `komira-bench-stage`, which prints the lines to commit, and a person commits them.

```text
komira-bench-stage tpch --duckdb <pinned duckdb> --tpch-extension <tpch.duckdb_extension.gz> \
    --cache-dir <dir> --scale-factor 1|10|100 [--memory-limit-gib 24]
komira-bench-stage verify --dataset clickbench --scale full --cache-dir <dir>
```

`tpch` first reads the extension gzip once and checks its size and sha256 against the pin for `--duckdb-version` and `--platform`: no pin, another file, another size or a non-gzip is refused (the message shows what was found and the line that would pin it) and nothing is created or started. The pinned bytes are unpacked into `<cache>/.komira-bench-stage` (made fresh with mode 0700, refused if it exists, removed after the run), so a file replaced after the check is never the file that runs. Then it checks the DuckDB file against its pin (`open_pinned`) and starts DuckDB with one thread, insertion order preserved and its spill directory in the private directory. It loads the unpacked copy and reads back whether `tpch` is loaded and from where: any install path other than that copy stops the run. It generates the eight tables and writes each to its manifest path, counts the rows of every written file with `read_parquet` and compares them with the manifest's row counts (lineitem at sf10 and sf100 is observed and printed), then verifies the directory and prints, for every file still unrecorded, a line of the form `out.append(RecordedFile("tpch/sf1/region.parquet", <bytes>, "<sha256>", <rows>))`. Paste those lines into `recorded_files()` in `manifest.mojo` (and the extension line into `tpch_extension_pins()`) in a pull request; from then on the verifier says `VERIFIED` or names the file that changed. `verify` does the same printing for a supplied dataset (ClickBench).

It never replaces anything, as a check before the first `COPY` (not an exclusive create: `COPY` overwrites, so another process of the same user creating a file in between could lose it): a directory with all eight files is only verified, one with some is refused (remove it by hand). A failed run stops DuckDB first, then removes the files it wrote and the empty `tpch/sf<N>` directories it made. The files are DuckDB's `dbgen` tables (DuckDB documents small differences from the specification's generator), so the board's TPC-H numbers are for these files, not audited TPC-H results; both engines read the same bytes. Native types are kept: `DECIMAL(15,2)`, `DATE`. The 122,880-row row group is DuckDB's default size; both settings are written out so that a changed default of a later release cannot change the files unnoticed; `STAGE_VERSION` names this set, and changing any of it means new recorded checksums.

Determinism: `dbgen` takes no seed, so the data is a function of the scale factor and the extension build, and with one thread and insertion order preserved the writer sees the rows in one order, so the same DuckDB build and extension should give the same bytes. That is expected, not yet shown: the tests use a fake DuckDB, so nothing here has compared two real runs. The first measurement should be taken twice (two cache directories, same lines) before anything is recorded.

## Supplying ClickBench

Put the single-file `hits` table at `clickbench/hits.parquet` under the cache directory, unmodified (105 columns, 99,997,497 rows, 14,779,976,446 bytes), then run `komira-bench-stage verify`. The size is recorded, so a truncated download is refused without hashing it; the sha256 is recorded from the first complete download.

## Verifying

`verify_dataset(manifest, cache_dir)` checks every file of the manifest under `cache_dir` and gives each one a status:

| status | meaning |
| --- | --- |
| `VERIFIED` | size and sha256 are recorded and both match |
| `UNRECORDED` | present, everything recorded matches, but the size or sha256 is not recorded yet; the observed values are in the check |
| `MISSING` | no regular file at the path (a directory counts as missing) |
| `SIZE_MISMATCH` | the size differs from the recorded one; the file is not hashed, so a truncated download is refused without reading it |
| `SHA_MISMATCH` | the sizes agree and the sha256 differs |

`report.is_verified()` is true only when every file is `VERIFIED`; `report.is_usable()` also accepts `UNRECORDED`. A symbolic link inside the cache directory is followed. The verifier does not read Parquet footers, so it does not check row counts: those are in the manifest and the lock for the reader of a result.

```text
var manifest = find_manifest("clickbench", "full")
var report = verify_dataset(manifest, cache_dir)   # cache_dir comes from a flag
print(report.render())
```

## The lock

A lock records, for one dataset at one scale, every file's observed size and sha256 and the manifest's row count, and ends with a fingerprint: the sha256 of every line above it. A result that names the fingerprint names exactly those bytes. `lock_from_report` refuses a report with a missing, truncated or altered file, so no lock describes files that failed. `write_lock_file` writes `<cache_dir>/locks/<dataset>_<scale>.lock` (one file per dataset and scale, so one cache directory holds the locks of every dataset in it) and never replaces an existing one; `read_lock_file(cache_dir, dataset, scale)` reads it back. `verify_against_lock(lock, cache_dir)` checks the files in a cache directory against the sizes and checksums a lock recorded, so a later run can show it used the bytes the lock names. `decode_lock` is strict: an edited byte, a missing or extra line, a repeated path or a path that leaves the directory is an error.

```text
komira-bench-data-lock/1
dataset tpch
scale sf1
generator -
file tpch/sf1/region.parquet 1000 <64 hex characters> 5
file tpch/sf1/lineitem.parquet 2000 <64 hex characters> -
fingerprint <64 hex characters>
```

```mojo
from std.testing import assert_equal, assert_raises
from komira_bench_data import DatasetLock, LockEntry, decode_lock, encode_lock

var sha = String("0123456789abcdef") * 4
var entries = List[LockEntry]()
entries.append(LockEntry(String("tpch/sf1/region.parquet"), 1000, sha, 5))
var lock = DatasetLock(String("tpch"), String("sf1"), String(), entries^)
var text = encode_lock(lock)
assert_equal(decode_lock(text).fingerprint(), lock.fingerprint())

with assert_raises(contains="fingerprint does not match"):
    _ = decode_lock(text.replace(" 1000 ", " 1001 "))
```

## The h2o-style generator

`h2o_groupby_parquet(rows, groups, seed)` and `h2o_join_parquet(table, rows, seed)` write the tables of the h2o db-benchmark's group-by and join data as Parquet bytes, with `komira_parquet_writer`. They have the columns and value ranges of that benchmark's files, and they are not its random stream (that is an R script): every value is a pure function of the seed, the column and the row number (SplitMix64's mixer), so the same seed and sizes give the same table on every machine and a row does not depend on the batch it is built in.

The same seed, row count, group count, codec and batch size give the same Parquet bytes. The batch size (`batch_rows`, 1,048,576 by default) is part of that identity: the writer chooses its encodings per row group and writes several batches that fit one row group without joining them first, so another batch size gives the same table in other bytes. The bytes also depend on `komira_parquet_writer`. The tests pin the SHA-256 of a small table of each kind, so a change to the generator or to the writer that alters those bytes is visible; it must come with a new `H2O_GENERATOR_VERSION` (which the manifest and the lock carry) and new pins, because every recorded checksum of a generated dataset changes with it.

```mojo
from std.testing import assert_equal, assert_true
from komira_bench_data import H2O_DEFAULT_SEED, h2o_groupby_parquet

var first = h2o_groupby_parquet(2000, 10, H2O_DEFAULT_SEED)
var second = h2o_groupby_parquet(2000, 10, H2O_DEFAULT_SEED)
assert_equal(len(first), len(second))
for i in range(len(first)):
    assert_equal(first[i], second[i])
assert_equal(first[0], UInt8(ord("P")))
```

`generate_h2o_groupby_files(cache_dir, rows, groups, seed)` and `generate_h2o_join_files(cache_dir, rows, seed)` write the files where the manifest says and return the manifest. They never replace a file: a dataset that is already there is verified, not regenerated. The manifest they return records the size and sha256 of the bytes written, so a file that is later cut short or altered no longer verifies; a write that fails removes the partial file.

The group-by table has `id1` and `id2` (strings `id001`..`id<k>`), `id3` (a string with ten digits, `rows // k` values), `id4` and `id5` (integers 1..k), `id6` (an integer 1..`rows // k`), `v1` and `v2` (integers 1..5) and `v3` (a double from 0 to 100 with six decimals). The join tables are `x` (N rows), `small` (N // 1,000,000 rows), `medium` (N // 1,000) and `big` (N rows), at least one row each; every key of `x` has a partner in the other three, and the key a table is unique on is spread over its rows by a seeded one-to-one map (a constant step modulo the table size, so every key appears once but the order is not a shuffle; for a table of a few rows the keys run in sequence from a rotated start).

Results on these tables are not comparable with published h2o db-benchmark numbers: the value distributions are uniform draws, not the original script's, and the generator has none of its NA or pre-sorted variants.

## Limits

- Generation builds the whole table in memory (all batches, then the encoded bytes), so memory is about the table plus its encoding. The manifest accepts up to 2,000,000,000 rows, but the sizes of the original benchmark (100 million to a billion rows) need a streaming writer, which is not part of this package yet.
- A process killed in the middle of a write leaves a partial file that the plain manifest, which records no size, reports as `UNRECORDED`; verify against the manifest the generator returned or against a lock.
- Row counts are carried, not checked: the verifier checks bytes and checksums.
- A cache directory is trusted as far as its files go: a symbolic link is followed.
- The package reads no environment and no configuration file; the cache directory is always an argument.
- Staging runs one DuckDB thread and builds the whole table in DuckDB's memory: sf10 needs a host with the memory limit it is given (24 GiB by default), and takes as long as one thread takes. sf100 is in the manifest but its staging has not been sized.
- The tests of staging run against a fake DuckDB. Whether the real `tpch` extension loads from a path, whether it reports that path as its install path (the run stops if not), and whether two real runs give the same bytes are settled by the first run on a benchmark host.
- A run that is killed (kill -9, power loss) can leave `<cache>/.komira-bench-stage` behind, and the next run then refuses with "already exists": check that no `komira-bench-stage` is running, then delete the directory. `--cache-dir` of `tpch` must be absolute, because DuckDB's read-back install path is compared with the copy's path.
- To stage on another platform or release, add a pin: download the gzip yourself, read its size and sha256 with `wc -c` and `sha256sum`, have a second person repeat it, and add the line the refusal message prints to `tpch_extension_pins()` in `stage_extension.mojo`. There is deliberately no flag that skips the pin.
- The sf10 and sf100 `lineitem` row counts are not recorded (the specification gives an approximate count, not an exact one); the first run observes and prints them.
